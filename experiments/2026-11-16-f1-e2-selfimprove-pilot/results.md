## Outcome

All 8 arms ran on the 16 replay days (S8-S23, 6,720 items, 5,184 phase-C items per arm). Pre-registered criteria:

| id | criterion | result |
|---|---|---|
| **S1** | true wrong-commit rate <= 0.05, every guarded arm | **pass** (7/7 arms; 0.0048 - 0.0115) |
| **S2** | share of days with phase-C risk > 0.05 <= 0.10 | **pass** (7/7 arms; worst 1/16 days) |
| **S3** | observed phase-C mean loss <= ACI certificate | **pass** (7/7 arms) |
| **S4** | `feedback-p0.9` - `frozen` PER <= -0.03, CI95 below 0 | **pass**: -0.2153, CI95 [-0.2492, -0.1767] |
| **S5** | null-input commits <= 5 % (target 0), every arm | **FAIL** in all 8 arms (281 - 325 of 640; uniform nulls commit) |
| **S6** | `shuffled-labels` - `frozen` PER > -0.01 and S1 holds | **pass**: +0.1870; S1 0.0048 |

Short version:
- **Learning from feedback works in this replay.** Feedback-only adaptation of the day input layer lowers the phase-C PER from 0.686 (frozen) to 0.470, close to the oracle (0.459).
- **The wrong-commit bound held through 16 daily updates in every guarded arm**, also when the decoder was destroyed (self-training, shuffled labels).
- **But the bound is close to vacuous here.** The base decoder is weak. 88 % - 100 % of commits are wrong. The bound counts wrong commits over all items, so rare commits pass it at any precision.
- **S5 fails.** The guarded loop has only a non-empty-text gate. Uniform null streams pass it and commit on almost every day. The fix is the M2-18 evidence gate.
- **Self-training compounds errors** (D1): PER rises to about 0.97 by day 6.

## Findings

### S5 fails: uniform null streams commit
- Uniform log-prob streams commit on almost every day: 276 - 317 of 320 per arm (about 19-20 of 20 per day). The only days with 0 uniform commits are days where the day threshold was high (frozen day 1 and day 7, `lambda_day` 0.25 and 0.23; feedback-p1.0 day 3, 0.23).
- Frame-shuffled real trials almost never commit: 0 - 6 of 320 per arm (<= 1.9 %). Alone, this part would pass S5.
- **Cause.** The guarded loop in `fidetype.trust.adaptive.GuardedUpdateLoop` uses `CommitGate()` with its default settings. That gate refuses only empty text. A uniform stream gives no neural evidence. But the word route (beam + word trigram) still produces a non-empty sentence from the language-model prior alone. The n-best scores of that sentence give a `p_top1` (at `T_s` = 50) of about 0.2, above most day thresholds (0.15 - 0.25). The uniform stream does not depend on the decoder version, so the day-layer updates cannot fix it.
- This is the known M2-18 / M2-19 failure (no-signal input commits). The fix exists: the evidence gate `CommitGate(max_guard_risk=...)` in `src/fidetype/trust/content.py` (M2-18; the P14-03 drop-in API turns it on by default). The pilot did not turn it on. The plan did not ask for it, and we do not change the plan after the runs.

### Naive fixed-threshold arm vs guarded (D2)
- The naive arm commits from item 1 of each day at the S7 threshold (0.151), with no recalibration, no monitor and no offer-only phases. It made 323 commits (302 wrong) vs 72 (70 wrong) in the guarded `feedback-p0.9` arm.
- True wrong-commit rate 0.0449: the point estimate is below alpha, but the CP95 upper limit (0.0502) is above alpha. Phase-C risk was above 0.05 on **4 of 16 days** (0.072, 0.062, 0.052, 0.070). That would fail S2.
- The guarded loop cut the wrong commits by a factor of about 4.3 at the same PER (0.4703 vs 0.4709).
- Cost of the guarantee in eWPM: none here (4.14 vs 4.14). The reason is not good news: almost all naive commits were wrong, so they gave no typing speed. With a stronger decoder, the cost will be real and must be measured again.

### Learning from feedback (S4, D3)
- The frozen decoder gets worse day by day (phase-C PER 0.475 on day 1, 0.752 on day 16): day-to-day drift. The feedback arms stay at about 0.43 - 0.54 on all days. The gain grows with time: first 4 days -0.100, last 4 days -0.281 (feedback-p0.9 - frozen).
- `p_notice` has almost no effect (PER 0.4707 / 0.4703 / 0.4700 for 0.5 / 0.9 / 1.0). The reason: the commits are rare, so only 0 - 33 of about 5,390 labels come from uncorrected wrong commits. Most labels come from **retypes** (`p_retype` = 0.8), because the truth is almost never in the top-5 offer (offer hit 1.1 %).
- **Oracle gap (D3):** feedback - oracle PER is +0.0113 / +0.0109 / +0.0106 for `p_notice` 0.5 / 0.9 / 1.0. The oracle has 6,694 labels, the feedback arms about 5,390. So the gap matches the label count, not the label noise.

> **Our take:** in this pilot, "feedback" is mostly "the user retypes 80 % of the sentences". That is close to supervised recalibration with 80 % of the labels. It shows that the loop works end to end. It does not yet show learning from cheap feedback (accept / reject only). A real user would not retype 80 % of the sentences. P15-03 must use a realistic retype rate (calibrated on `t15_personalUse.pkl` when it is local) and a stronger decoder, so that accepts give the main label source.

### Self-training compounds errors (D1)
- `selftrain` - `frozen` PER: mean +0.2048, CI95 [0.1700, 0.2358]; first 4 days +0.092, last 4 days +0.217; slope +0.0095 per day. The selftrain PER goes from 0.485 (day 1) to 0.933 (day 5) and stays at about 0.96 - 0.97 from day 6. The decoder collapses.
- All 5,902 self-labels are wrong (the decoder's top-1 sentence is almost never exact). So this arm trains on wrong text only.
- Expectation of the plan (self-training worse than feedback): confirmed. It is the ALIGN 2026 warning in its strongest form.

### Shuffled-labels null (S6)
- Training the day layer on permuted true labels does not "learn": PER +0.1870 vs frozen (0.8726 vs 0.6856). It destroys the layer on day 1 (0.652) and stays at about 0.85 - 0.91.
- S1 holds for this arm (0.0048). The trust layer recalibrated after each bad update and committed less (32 commits). This is the behaviour we want: a broken decoder update must not break the bound.

### Vacuity caveat: the bound is over all items, not over commits
- Error among commits is 0.885 - 1.000 in every guarded arm. The frozen arm made 65 commits and **all 65 were wrong**. `feedback-p0.9` made 72 commits, 70 wrong.
- S1 passes because commits are rare (about 1 % of items): wrong commits / all items is small even if every commit is wrong. A system that commits 1 % of the time at random would also pass.
- The ACI certificate (about 0.0494) is close to alpha plus a small slack. The observed losses (0.005 - 0.014) were far below alpha, so the ACI threshold went down to 0.0 in six of the seven guarded arms (0.0675 in frozen). So `lambda_aci` never limited the commits. The commits were limited only by the day threshold `lambda_day` from `block_ltt`.
- So the pilot shows that the bound **stays valid** through updates. It does not show that the bound is **useful**. A useful guarantee needs a precision-type risk (wrong commits / commits; roadmap P5-02) or a decoder good enough that commits are mostly right.

### Sentence temperature at the grid edge
- `T_s` = 50 is the top value of the grid 1 .. 50 (minimum Brier score on S7). The true optimum may be higher. A high `T_s` makes `p_top1` flat (about 0.15 - 0.25 for all items), so the score separates right from wrong sentences poorly. This is one reason for the low precision of the commits.
- On S7 the top-1 sentence was right on only 1.3 % of phase-C items. With so few right items, the Brier score prefers a flat score.

## Deviations from the plan
1. **Own small CPU decoder, not the T12 v2 decoder.** This was already stated in the plan (section "Why not the T12 v2 decoder or its logits"): the v2 logits already contain the per-day adaptation of all 24 sessions, and the v2 checkpoint lies in a folder that this task must not touch. The roadmap item lists "T12 v2 decoder" as a dependency; we used only the v2 feature files (read only). The base decoder is weaker than v2 (S0-S6 val PER 0.445 at epoch 9; v2: 0.269).
2. **Smoke-path environment variables in `replay.py`.** `F1E2_ROOT`, `F1E2_ARMS` and `F1E2_TUNE` override the output, arm and tuning paths for smoke tests only. The defaults are the plan paths. All 8 real arms used the defaults. The edit is in commit `997aa93`, before the tuning and replay runs. It does not change any result.

No other change to the plan, the grid, the arms, the criteria or the metrics.

## What this means for F1
- The replay simulator, the simulated user, feedback-only adaptation and the guarded update loop work end to end on 16 real days. The roadmap "Done when" of P15-01 is met: all arms ran and were compared with the pre-registered criteria.
- Two of the three parts of the F1 claim have first evidence: the decoder improves from feedback (S4), and the long-run bound stays valid through every daily update, also under bad updates (S1-S3, S6). The negative control behaves as predicted (D1).
- The third part, "never puts words in the user's mouth", **fails** on no-signal input (S5) without the evidence gate. No F1 claim may be made until the update loop refuses null inputs after every update.
- The positive results are weak evidence because of the weak base decoder (almost all commits wrong) and the high retype rate. We do not quote this pilot as F1 evidence in public. It is a working harness for P15-02 / P15-03.

## Follow-up for the GPU runs (P15-03) and P15-02
1. **Main fix: evidence commit gate plus a per-update null refusal in `GuardedUpdateLoop`.** Use `CommitGate(max_guard_risk=...)` (M2-18) in phase C. After each update, run the uniform and frame-shuffled null controls; if more than the allowed share commits, refuse the update (keep the champion) or set the day to offer-only. This is the P15-02 "null controls on every update" requirement; add a unit test that a version which commits on uniform input is refused.
2. **Stronger base decoder** on the first K sessions (GPU; for example a GRU trunk as in v2), so that commits are mostly right and the bound is not vacuous. Report error among commits next to the bound.
3. **Extend the `T_s` grid** above 50, or use a score with a better separation (for example the margin to the second sentence or the phoneme posterior).
4. **2 - 3 simulated-user seeds** and a realistic `p_retype` (much lower than 0.8; calibrated on `t15_personalUse.pkl` when local), so that most labels come from accepts.
5. **T15 (45 sessions over 20 months)** as the second dataset.
6. **Semi-bandit feedback risk control (P15-04):** the observed loss sees only what was shown or corrected; compare it with `aci`.
7. **Silent-error margin:** silent errors are not covered by any of the bounds. At `p_notice` 0.5, 33 of 77 wrong commits were silent (observed rate 0.0065 vs true 0.0115). Add a stated margin, for example run the online control at alpha x `p_notice_min`, or report the true rate under an assumed `p_notice`.
8. A precision-type risk (P5-02) so that the guarantee says something about the commits themselves.
