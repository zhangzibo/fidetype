# P15-02: gated re-run of the F1 / E2 CPU pilot (results)

The P15-01 pilot ([results](results.md), [plan](plan.md)) failed S5: uniform null streams committed in every arm. P15-02 made `fidetype.trust.adaptive.GuardedUpdateLoop` safe by construction (commit `8f2d2c7`). This page re-runs two pilot arms with the new loop.

## What changed against P15-01

| # | change | detail |
|---|---|---|
| 1 | evidence commit gate on | loop default `DEFAULT_EVIDENCE_GATE = CommitGate(min_chars=1, min_words=0, max_guard_risk=1.0)` (M2-18). Guard risk = `HallucinationGuard().score(nbest)` on the word n-best. A decision without a guard risk never commits. The loop refuses to start without an evidence gate unless `unsafe=True`. |
| 2 | null refusal on every update | after the check block, 20 uniform and 20 frame-shuffled null inputs of the day go through the new version. A control with more than `floor(alpha * n)` = 1 commit rejects the update. |
| 3 | champion / challenger | champion = day-start decoder (`<day>-u0`); challenger = phase-A update (`<day>-u1`). Paired exact sign test on top-1 errors of the check block (48 items, level 0.05). A rejected challenger rolls back to the champion. Each accepted update gets a new `config_id`, chained to its parent; `audit_records()` gives one record per update. |

Not a plan change: the P15-01 plan, arms and criteria are the same. This is a second run with a changed loop, so we report it next to the original, not in place of it.

## Update decisions and null controls

| arm | updates | accepted | rejected | null controls passed (uniform / shuffled) | sign-test p-values | alarms |
|---|---|---|---|---|---|---|
| frozen | 16 | 16 | 0 | 16/16 / 16/16 | all 1.0 | 0 |
| feedback-p0.9 | 16 | 16 | 0 | 16/16 / 16/16 | 1.0 (14 days), 0.5 (2 days) | 1 (day S16) |

- Every update was accepted. Every accepted update got a new `config_id`, chained to the previous one (final `gul-afee9e569f766a13` frozen, `gul-63f5fdbc8ba511dd` feedback-p0.9).
- **The champion / challenger test has no power here.** The loss is top-1 sentence exact. On the 48 check items, the champion and the challenger were both wrong on 45-48 items. Discordant pairs: 0-1 per day. A sign test with at most 1 discordant pair can never refuse. So "accepted" means only "not shown to be worse", not "better".
- The per-update null controls passed on every day. The uniform guard risk was 1.0 on every day (`uniform_guard_risk_min` = 1.0), and the gate commits only below `max_guard_risk` = 1.0. So the uniform refusal rests on a saturated guard score at the gate limit. A guard that gives uniform input a risk just below 1.0 would let it through. P15-03 must report the guard-risk margin, or use a stricter limit fitted on data.

## Conclusion

- **The P15-02 loop fixes the P15-01 S5 failure.** With the evidence gate default and the per-update null refusal, uniform null input commits 0 / 640 times across both arms (original 590 / 640). S1-S4 still pass. The learning effect (S4) is the same.
- **The guarantee is still close to vacuous.** 89-100 % of commits are wrong. The bound counts wrong commits over all items, so rare wrong commits pass it. This needs a better decoder and a precision-type risk, not a better gate.
- **The champion / challenger gate is untested on real data.** With an exact-sentence loss and a weak decoder, the sign test cannot see a difference. The unit tests show that it refuses a worse challenger. The replay does not show it.

### What P15-03 (GPU runs) must do
1. Use a stronger base decoder (GPU, a GRU trunk as in v2), so that a real share of commits is right.
2. Report error among commits next to the bound, for every arm.
3. Use a champion / challenger loss with more signal than top-1 exact: for example the phoneme error rate per item (paired test on PER differences) or a word-level loss. A sign test with almost no discordant pairs is not a check.
4. Report the guard-risk margin of the null inputs (how far below 1.0 the real items are, and how close the null items come to the limit). Fit `max_guard_risk` on calibration data instead of the fixed 1.0.
5. Run all arms (also `shuffled-labels` for S6, `selftrain` for D1), 2-3 user seeds, a realistic retype rate, and T15.

### What P5-02 (precision-type risk) must do
- Give a bound on wrong commits / commits (the FDR-type risk), not only wrong commits / items. The loop already reports block precision (`block_wrong_among_commits`) and can gate on it (`max_wrong_among_commits`). In this re-run the option was off (`None`), and every check block (16 days x 2 arms) had 0 commits, so it had no data. P5-02 must give a calibrated limit with a stated confidence.

## P15-02 roadmap status

The roadmap "Done when" asks for unit tests that (a) refuse a worse challenger, (b) refuse a challenger that fails the null controls, and (c) change the `config_id` on every accepted update, running in CI. All three exist in `tests/test_trust_adaptive.py` (`test_worse_challenger_is_refused_and_champion_comes_back`, `test_update_that_commits_on_uniform_input_is_rejected`, `test_frame_shuffled_failure_is_rejected_and_rate_is_floor_alpha_n`, `test_config_id_changes_on_every_accepted_update_and_audit_records`; 29 tests pass).

Not done from the P15-02 deliverable:
- **Hooks in `TrustGuard` / `OnlineTrustPolicy`.** The update loop lives in `GuardedUpdateLoop` only. The P14-03 drop-in API (`TrustGuard`) and `OnlineTrustPolicy` do not yet know when the decoder changes, and they do not yet re-run calibration and null controls on an update.
- **Ledger record per update.** Updates give `UpdateRecord`s through `audit_records()` (in the arm JSON here). They are not yet written to the trust-layer JSONL audit log / ledger of `TrustGuard`.
- **Block test on the challenger.** The deliverable names `block_test` / `block_ltt`; the loop uses a paired sign test. The session threshold is still refitted by `block_ltt` on each update.

Status: **in_progress**. Remaining part: the `TrustGuard` / `OnlineTrustPolicy` hooks and the ledger record per update.
